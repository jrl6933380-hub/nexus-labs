Nexus Forge is a business, not a page. It's the caller-led website sales operation: workers get qualified local-business leads, review the business, open a pre-generated replacement site, use a tailored pitch, call the prospect, and log the outcome. It spans three distinct surfaces — never answer "is Forge ready?" without saying which one is meant:

- Forge Builder (`/room.html`) — the build tool. Create and live-edit a site/room/tool. Formerly called "Room Builder"; same page, renamed. Internal slug is still `room-builder` and URL is still `/room.html` — load-bearing, unchanged.
- Forge Field (`/forge-caller.html`) — the worker workspace: assigned leads, business intel, site preview, pitch guide, tap-to-call, outcome logging.
- Forge Ops (`/forge-dashboard.html`) — the operator/manager view: customer accounts, plans, usage, billing status, granting credits.

Forge Builder's customer contract is automatic completion, not ticket routing. An explicit create/edit request goes into the live builder even when it is ambitious. Complexity may cause Nex to scope a complete first version, retry, or pull in another model behind the scenes; it must not make the customer supervise agents or wait on a Build Team ticket. Escalation records are for verified product capability gaps and old operational recovery only, never a normal fallback for provider errors, timeouts, truncation, or a request that needs more than one model pass. Customer-facing generation runs through each signed-in customer's connected Builder Brain. There is no owner-funded fallback: if the customer's provider connection is missing or unhealthy, explain the exact setup or recovery step instead of spending a centrally funded AI key. OpenRouter is the recommended adapter and provider credentials stay encrypted behind the server-side connection boundary.

Billing is live, not theoretical. There is a real Stripe account ("Nexus OS") and real server-side code: `api/checkout.js` creates live Checkout Sessions for plan upgrades and credit packs (auth-gated, price resolution via `lib/billingPlans.js`, project-scoped purchase validation), `api/billing-portal.js` handles customer billing management, `api/webhooks/stripe.js` handles Stripe events. Old task notes claiming billing is "not yet wired" are out of date — do not repeat that phrasing. If asked about billing specifics, check the actual code and the Stripe account, not a cached claim.

The Board task "New venture: Nexus Forge" is a product-direction write-up, not a unit of work — its status sitting at "testing" is not a readiness signal. Real Forge planning lives in the venture's own room (`/canvas.html?id=nexus-forge`): Upgrades, Profitability, Marketing, Developer View sections are real and readable/contributable.

The standing lesson behind all of this: a Board task's `result` field is a snapshot of what was true when written, not current state. Verify readiness claims against live code, the live Stripe account, or the live deployment — never against a task result alone.

This skill is domain knowledge only. It does not grant tools, credentials, approvals, deployment authority, or permission to change billing/checkout code — those changes still need their own branch, tests, and PR review given they touch billing.

Nex has read tools for real-time Forge visibility, not just this static domain description: `list_forge_customers` (every BILLING account — plan, usage, live Stripe status, same data as the Ops dashboard) and `list_forge_escalations` (every Build Team ticket in flight, with status, so you don't need a specific escalation id handed to you). Follow up with `get_forge_escalation` for a ticket's full request text, or `get_tunneled_pipeline` for build detail. `submit_pipeline_lane_result` and `submit_pipeline_review` let you actually step into a stuck build — take over the work yourself with your normal repo tools, then submit real evidence — rather than only watching from the outside. `delete_forge_escalation` permanently removes a dead or stale escalation record; deleting its Board tasks alone does NOT do this, and the record will keep resurfacing in `list_forge_escalations` as if it were live work. Confirm with Mr. Lopez before deleting anything that might be a real customer's request.

To look up accounts, use `find_forge_account` (one username — does it exist, what plan, what Forge role) or `list_forge_accounts` (all accounts, optionally filtered by role or plan). These cover EVERY account, free and test ones included. `list_forge_customers` is a billing view: it deliberately covers only accounts on a paid plan or with Stripe history, so an ordinary free account does not appear there. An empty or missing result from `list_forge_customers` is therefore NOT evidence that an account does not exist — that mistake has already been made once, reporting a healthy account as nonexistent. Neither lookup returns credentials; a password cannot be read back after creation, only reset.

`create_forge_account` provisions a real account and returns its password once. Use it when Mr. Lopez asks for a worker or manager account for Forge Field, or a test account. `kind: 'worker'` seats forge_worker, `'manager'` seats forge_manager, `'customer'` (the default) creates an ordinary account with no Forge role — that is normally what a test account should be, and leaving `plan` unset keeps it on the free tier so it exercises the same publish gate and metering a real customer hits. The password is shown once and cannot be read back, so pass it on in your reply. You cannot create an operator: operator status comes from the NEXUS_OPERATOR_USERNAMES environment variable and is deliberately out of reach at runtime, so no agent can escalate an account. An existing username is refused rather than overwritten, which protects the credentials and history already attached to it.

`delete_forge_account` permanently removes an account — the record, its Stripe reverse-index entry, and every live session, so it cannot stay signed in on an old cookie. It is irreversible with no backup, so confirm with Mr. Lopez before deleting anything that might belong to a real person, and look it up with `find_forge_account` first so you can say what you are about to destroy. Two refusals are not overridable: an operator account (deleting the record would remove their login while leaving their environment-derived privileges intact, locking Mr. Lopez out of his own admin surface), and an account with billing on record unless you pass `acknowledge_billing` — deleting does NOT cancel a Stripe subscription, so that customer would keep paying for a login that no longer exists. Cancel the subscription first.

How a Forge build job actually runs (as of PR #291): a job is NOT split into parallel lanes by default. `start_tunneled_pipeline` defaults to `mode: 'solo'` — one builder owns the job end to end, and can call `ask_helper_model` to get a second model's opinion on one specific question when it is genuinely stuck. Pull in extra help when the work needs it; do not fan a job out across models by default. The old layout+design split is still available as `mode: 'dual'` if a job genuinely warrants two independent perspectives, but it is the exception, not the norm.

Two operational lessons worth keeping, both learned the hard way: (1) Do not relaunch a pipeline for an escalation that already has one running — check first. Five concurrent runs were once started for a single escalation, which saturated the AI Gateway and took down Mr. Lopez's own live chat. His conversation with you outranks any background retry. (2) A backlogged escalation is not automatically real work. Old test escalations sat around looking like a customer backlog and got repeatedly "fixed" when they should have been deleted. Before grinding on a stale ticket, ask whether it is something Mr. Lopez actually wants built.
