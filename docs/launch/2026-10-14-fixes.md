## Rest schedule and queue limitations

Set `NEX_POD_REST_START` and `NEX_POD_REST_END` as `HH:MM`, plus `NEX_POD_SCHEDULE_TIMEZONE` (defaults to America/Chicago). With no valid schedule, the system stays unscheduled and real model failures remain outages. This PR does not invent or activate an operating schedule and never powers on a pod.

Team assignments already saved in their durable queue remain available to the existing sweep. Owner chat requests wait in tenant-scoped status storage; an open/reopened authenticated conversation resumes them. Customer chat requests wait in account-scoped browser storage and resume in the open/reopened app. Closed-app autonomous chat execution at opening time is not implemented here. Availability means the scheduled time window, not a successful live health check. The pod must already be running before inference can succeed.

Justin handles merges. No production merge or live benchmark was performed.
